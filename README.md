## 1. 프로그램 개요

tomolog는 여러 사람이 한 방에 모여 같이 공부하는 실시간 스터디 룸 서버다. 방에 들어가면 공유
포모도로 타이머로 같이 집중하고, 누가 접속해 있는지 실시간으로 보이고, 한 사이클이 끝나면 공부
기록(이모지 + 한 줄 메모 + 공부한 시간)을 남겨 방 피드에 쌓는다. 꾸준히 하면 스트릭이 오르고,
조건을 채우면 뱃지를 받고, 방마다 같이 키우는 펫이 자란다.

과제 범위는 서버까지다. 화면(프론트엔드)은 만들지 않았고, 대신 REST API와 STOMP(WebSocket),
그리고 테스트 코드로 동작을 검증할 수 있게 했다.

만들면서 제일 신경 쓴 한 가지는 동시성이다. 인기 방에 사람이 한꺼번에 몰려도 정원을 절대 넘지
않게 하는 것이다. 기능을 늘리는 것보다 이게 더 중요하다고 봤고, 한 가지가 아니라 네 가지 전략으로
풀어서 테스트로 증명했다(5번, [docs/CONCURRENCY.md](docs/CONCURRENCY.md)).

기술 스택:

- Java 21, Spring Boot 3.3
- PostgreSQL (Flyway로 스키마 버전 관리), Redis (분산 락)
- OAuth2 (구글·카카오) + JWT, STOMP 실시간 메시징
- 4계층 + 헥사고날 구조
- CI에서 포맷·린트·복잡도·아키텍처·커버리지·동시성 테스트를 전부 검사

## 2. 사용한 주요 자바 개념

문법을 나열하기보다 어디에 왜 썼는지로 적는다.

- **record (불변 DTO)**: 컨트롤러가 주고받는 요청·응답을 전부 record로 뒀다. JPA 엔티티는 바깥으로
  내보내지 않고, 입력은 Bean Validation으로 검증한다.
- **enum**: 방 타입(PRIVATE/THEMED), 방 상태, 입장 전략 종류, 타이머 페이즈, 뱃지 종류를 enum으로
  뒀다. 분기와 DB 저장이 안전해진다.
- **인터페이스 + 전략 패턴**: 입장 방식이 네 가지(비관/낙관/분산/원자)인데 if문으로 늘어놓지 않고
  `RoomJoinStrategy` 인터페이스 하나로 맞췄다. 방 타입에 따라 구현만 갈아끼우고, 같은 테스트로 네
  전략을 똑같이 검증한다.
- **제네릭 / Optional**: 리포지토리 포트와 조회에 사용했다. null 대신 Optional을 돌려준다.
- **동시성 도구**: 테스트에서 `ExecutorService`와 `CountDownLatch`로 진짜 "동시 출발"을 만든다.
  타이머 상태는 `ReentrantLock`으로 보호한다. 입장 카운터는 단일 JVM의 `synchronized`가 아니라
  DB 레벨(`SELECT FOR UPDATE`, `@Version`, 조건부 UPDATE)과 Redis 분산 락으로 막는다.
- **스트림**: 엔티티-도메인 매핑과 집계(뱃지 목록 등)에 사용했다.
- **예외 계층**: 도메인 예외(`ApiException`)와 에러 코드로 묶고, `GlobalExceptionHandler`에서
  HTTP 응답으로 변환한다.

## 3. 클래스 구성 설명

패키지는 4계층이고 의존은 위에서 아래로만 흐른다. 가장 안쪽 domain은 스프링도 JPA도 모른다. 이
방향은 ArchUnit 테스트로 강제해서, 거꾸로 의존하면 빌드가 깨진다.

```
com.tomolog
├── presentation    REST 컨트롤러 + STOMP 핸들러 (DTO record로만 주고받음)
├── application     유스케이스 서비스. 트랜잭션 경계, 입장 전략 라우팅
├── domain          순수 도메인 모델 + 포트(리포지토리 인터페이스). 프레임워크 의존 없음
└── infrastructure  JPA 어댑터 / 동시성 전략 / jwt·oauth·security
```

애그리거트(방·유저·멤버·로그·펫·뱃지)마다 다섯 조각으로 나눴다: 도메인 모델 / 포트 인터페이스 /
JPA 엔티티 / 매퍼 / 영속성 어댑터. 예를 들어 방은 `domain/room/Room`이 규칙(정원 검사 등)만 갖고,
저장은 `infrastructure/persistence/room`의 엔티티·어댑터가 맡는다.

핵심 클래스:

| 클래스 | 역할 |
| --- | --- |
| `RoomService` | 방 생성·입장·퇴장. 방 타입을 보고 입장 전략을 고른다 |
| `RoomJoinStrategy` + 4구현 | 정원 보호 (비관/낙관/분산/원자) |
| `PomodoroTimerService` + `TimerScheduler` | 공유 타이머. 1초마다 틱을 브로드캐스트 |
| `LogService` | 공부 기록 저장 + 게이미피케이션 + 이벤트 발행 |
| `GamificationService` | 스트릭·펫·뱃지 갱신 |

엔티티 6개의 관계도(ERD)와 컬럼별 설계 의도는 따로 정리했다 →
[docs/DATA-MODEL.md](docs/DATA-MODEL.md)

## 4. 실행 방법

```bash
docker compose up --build      # app + postgres + redis 가 함께 뜬다
```

한 번에 세 컨테이너가 모두 정상(healthy)으로 올라온다.

![docker compose up](docs/images/docker-compose-up.png)

- 앱 주소: http://localhost:8080
- 실제 구글/카카오 키가 없어도, 로컬·테스트 프로필에서는 개발용 로그인으로 토큰을 받을 수 있다.

  ```bash
  curl -X POST localhost:8080/api/auth/dev-login -H 'Content-Type: application/json' -d '{"oauthId":"demo"}'
  # → {"accessToken":"...","tokenType":"Bearer"}   이후 Authorization: Bearer <token>
  ```

- 환경변수는 `.env.example`을 참고한다(시크릿은 커밋하지 않는다).
- 전체 API는 Swagger UI에서 바로 실행해 볼 수 있다: http://localhost:8080/swagger-ui.html

![Swagger UI](docs/images/swagger-ui.png)

빌드와 테스트:

```bash
./gradlew build         # 포맷·체크스타일·PMD·테스트·커버리지·ArchUnit 전체 게이트 (Docker 필요)
./gradlew stressTest    # 대규모 부하 탐색 — 기본 빌드엔 미포함
```

## 5. 주요 기능 설명

### 방과 입장 (동시성)

방은 두 종류다. 호스트가 만들고 정원을 정하는 친구방(최대 50명)과, 미리 만들어 둔 큰 테마방
5곳(각 2000명)이다. 입장은 어떤 경우에도 정원을 넘지 않아야 한다.

이걸 한 방법으로만 풀지 않고, 트레이드오프가 다른 네 전략으로 만들었다. 친구방은 설정값으로
비관·낙관·분산 락 중 하나를 쓰고, 대규모 테마방은 임계 구간이 한 문장인 원자적 전략을 쓴다.

네 전략은 같은 합격 테스트를 통과한다. 정원 4명짜리 방에 100개 스레드가 동시에 달려들면 정확히
4명만 성공하고 나머지는 거절되며, DB에도 정확히 4명만 남는다.

![동시성 합격 테스트](docs/images/concurrency-test.png)

부하 테스트로는 2만 동시 입장까지 밀어 봐도 초과가 0명이었다. 자세한 전략 비교, 부하 측정, 가드를
일부러 부숴서 검증한 과정은 따로 정리했다 → [docs/CONCURRENCY.md](docs/CONCURRENCY.md)

### 실시간 공유 타이머

방마다 포모도로 타이머가 돈다. 서버가 1초마다 틱을 계산해 방 전체에 STOMP로 쏘기 때문에, 한 방에
있는 모두가 어긋남 없이 같은 시계를 본다. 페이즈는 집중 25분 / 휴식 5분이고, 시작·일시정지·건너뛰기
제어는 호스트만 할 수 있다. 타이머 상태는 방별 인메모리로 들고 있다(단일 서버 전제, 6번 참고).

타이머와 공부 기록은 일부러 느슨하게 묶었다. 집중이 끝났다고 서버가 자동으로 기록을 남기지는
않는다. 사용자가 직접 기록을 제출하고, 그 제출이 스트릭·펫·뱃지를 갱신한다.

### 공부 기록과 피드

한 사이클이 끝나면 이모지 + 한 줄 메모 + 공부한 분을 기록으로 남긴다. 같은 방 멤버만 남길 수 있고,
새 기록이 생기면 방 토픽으로 실시간 브로드캐스트되어 피드에 쌓인다.

### 게이미피케이션 (스트릭·펫·뱃지)

기록을 제출하면 한 트랜잭션 안에서 세 가지가 갱신된다.

- **스트릭**: 어제 공부했고 오늘 또 하면 +1, 하루라도 비면 1로 리셋. 같은 날 여러 번 해도 그대로.
  최장 기록(longest)은 줄지 않는다.
- **방 펫**: 그 방의 누군가 공부할 때마다 공부한 분이 성장 포인트가 된다. 100포인트마다 레벨 1씩.
  여러 명이 동시에 공부해도 포인트가 새지 않게 원자적으로 올린다.
- **뱃지**: 첫 기록(FIRST_LOG), 7일 연속(STREAK_7), 새벽 공부(NIGHT_OWL), 한 번에 120분 이상
  (MARATHON). 같은 뱃지는 한 번만 지급된다(DB 유니크 제약).

`GET /api/stats/me`로 현재 스트릭·최장 스트릭·총 공부시간·획득 뱃지를 조회한다.

### REST · 실시간 API 요약

| Method | Path | 설명 |
| --- | --- | --- |
| POST | `/api/auth/dev-login` | (local/test) 개발용 JWT 발급 |
| GET / PATCH | `/api/users/me` | 내 프로필 조회·수정 |
| POST / GET | `/api/rooms` | 방 생성 / 목록 |
| GET | `/api/rooms/{id}` | 방 상세(+멤버) |
| POST | `/api/rooms/{id}/join` | 동시성 보호 입장 |
| DELETE | `/api/rooms/{id}/members/me` | 퇴장 |
| POST / GET | `/api/rooms/{id}/logs` | 기록 제출 / 피드 |
| GET | `/api/stats/me` | 스트릭·총시간·뱃지 |

실시간은 `/ws`로 접속(STOMP CONNECT 프레임에 JWT)하고 `/topic/rooms/{id}`를 구독하면
입장·접속상태·새 기록·타이머 틱·펫 성장 이벤트가 온다. `/app/rooms/{id}/{chat|presence|timer/control}`
로 채팅·접속상태·타이머 제어를 보낸다.

## 6. 본인이 구현한 부분

이 프로젝트는 AI 에이전트로 코드를 많이 썼다(7번에서 솔직히 밝힌다). 그래서 "내가 한 부분"은 코드
타이핑이 아니라 설계 결정, 검증, 버그 추적이다.

**설계 결정을 직접 내렸다.** 아래는 모두 내가 정하고 근거를 의사결정 원장(`docs/DECISIONS.md`)에
남긴 것이다.

- 방을 친구방/테마방 두 종류로 나누고 타입별로 입장 전략을 분리했다(LEDGER-008). 모든 방을 같은
  전략으로 처리하는 안, 서비스를 물리적으로 쪼개는 안과 비교한 뒤 골랐다.
- DB를 MySQL에서 PostgreSQL로 바꿨다(LEDGER-006). 매니지드 호스팅 가능성을 열되, 인증·실시간은
  매니지드를 쓰지 않고 OAuth2·STOMP를 직접 구현했다. 이게 과제에서 보여줘야 할 부분이라 봤다.
- 4계층 + 헥사고날 구조를 택했다(LEDGER-007, LEDGER-010). 핵심 규칙이 JPA 엔티티에 섞이는 게
  싫어서 도메인을 순수 객체로 분리했다.

**직접 검증하고 버그를 잡았다.**

- 원자적 입장에서 카운터를 보상(decrement)하던 코드가 롤백과 겹쳐 카운터를 망가뜨리던 걸
  찾아냈다. 증가와 멤버 삽입을 한 트랜잭션에 묶으면 롤백이 알아서 되돌린다는 걸 알고 보상 코드를
  지웠다.
- 테마방 퇴장에서 멤버 삭제와 카운터 감소의 순서가 어긋나던 걸 바로잡았다(삭제를 먼저 flush).
- 가드가 진짜 일하는지 일부러 부숴서 확인했다. 정원 조건 한 줄을 빼니 테스트가 빨갛게 떴고,
  되돌렸다. (자세히 → [docs/CONCURRENCY.md](docs/CONCURRENCY.md))

**한계도 숨기지 않고 적었다.** 공유 타이머는 단일 서버 전제다. 여러 인스턴스로 띄우면 인스턴스마다
틱을 쏴서 신호가 중복된다. 리더 선출(ShedLock 등)로 막을 수 있지만 과제 범위에 과해서 지금은
한계만 명시하고 자리만 비워 뒀다(LEDGER-009).

## 7. AI 활용 여부 및 활용 범위 (바이브코딩)

솔직히 적는다. 이 프로젝트는 AI 에이전트(Claude Code)를 적극 활용한 바이브코딩으로 만들었다. 코드
타이핑은 AI가 더 많이 했다. 다만 그냥 시킨 게 아니라, AI가 멋대로 가지 못하게 규칙을 먼저 깔고 그
안에서만 일하게 만든 것이 이 프로젝트에서 가장 공들인 부분이다.

먼저 운영 규칙(`CLAUDE.md`)과 빌드 스펙(`SPEC.md`)을 직접 설계했다. 핵심 원칙은 "증명할 수 있는
건 증명하고, 못 하는 건 사람에게 묻는다"였다. 그래서 모든 작업을 두 갈래로 나눴다.

- VERIFIED: 테스트·타입·아키텍처 검사로 증명되는 것. 증거(테스트 이름, 명령)를 남긴다.
- ASSUMED: 내 도메인 판단에 기댄 것. 코드에 표시하고 의사결정 원장(`docs/DECISIONS.md`)에 남겨,
  슬그머니 결정되는 게 없게 했다.

그리고 포맷·린트·복잡도·커버리지·아키텍처 검사를 자동 게이트로 묶어, 통과 못 하면 빌드 자체가
실패하게 만들었다. 테스트를 비활성화하거나 커버리지 임계치를 낮추는 편집은 훅으로 물리적으로
차단했다. AI의 확률적 판단을 믿는 대신, 지켜야 할 건 기계가 강제하도록 한 것이다.

이 구조 덕분에 내 역할은 코드를 받아치는 게 아니라 방향을 정하고 결과를 검증하고 틀린 걸 잡아내는
것이 됐다. 6번에 적은 버그들이 실제로 그렇게 잡아낸 것이다.
