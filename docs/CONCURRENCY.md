# 동시성 제어 — 방 입장과 정원

이 프로젝트의 간판 기능이다. 인기 방에 사람이 한꺼번에 몰려도 정원을 넘지 않게 하는 것을 1순위
목표로 잡고, 한 가지 방법이 아니라 트레이드오프가 다른 네 가지 전략으로 풀었다. 그리고 "정원이
안 넘는다"를 말이 아니라 테스트로 증명했다.

요약은 README 6번에 있고, 이 문서는 그 근거를 자세히 적은 것이다.

---

## 1. 왜 방을 두 종류로 나눴나 (LEDGER-008)

처음엔 방이 한 종류였다. 정원을 누가 정하느냐를 고민하다 두 종류로 갈랐다.

| 타입 | 정원 | 호스트 | 만드는 법 | 입장 전략 |
| --- | --- | --- | --- | --- |
| PRIVATE (친구방) | 2~50, 호스트가 지정 | 있음 | `POST /api/rooms` | 설정값(비관/낙관/분산 중 하나) |
| THEMED (테마방) | 2000 고정 | 없음 | Flyway V3로 5개 사전 생성 | 항상 원자적 |

나눈 진짜 이유는 정원 숫자가 아니라 동시성 성격이다. 50명짜리 친구방은 입장할 때 방 행을 잠가
한 명씩 처리해도 느리지 않다. 그런데 2000명이 한 방에 몰리면 그 방식은 단일 행 잠금이 병목이
된다. 그래서 큰 방은 잠금 없이 한 문장으로 끝나는 원자적 전략을 쓰도록 타입별로 갈랐다.

테마방 5개는 마이그레이션으로 미리 박아 둔 "장소"다: 분위기 좋은 카페, 제주 바다속 카페, 심야
도서관, 루프탑 스터디, 숲속 오두막. 전부 `capacity=2000`, 호스트 없음.

---

## 2. 정원이 정해지고 지켜지는 순서

**(1) 정원이 정해진다.** 친구방은 클라이언트가 보낸 값을 `RoomService.createRoom`이 2~50
범위로 검증한다. 벗어나면 거절. 상한은 도메인 상수로 못박혀 있다.

```java
// domain/room/Room.java
public static final int PRIVATE_MAX_CAPACITY = 50;
public static final int THEMED_MAX_CAPACITY = 2000;
```

**(2) 타입이 전략을 고른다.** 입장 시점에 `RoomService.join`이 방 타입을 보고 라우팅한다.

```java
RoomJoinStrategy strategy =
    type == RoomType.THEMED
        ? joinStrategyResolver.strategyFor(JoinStrategyType.ATOMIC) // 큰 방
        : joinStrategyResolver.active();                            // 친구방
```

**(3) 정원이 지켜진다.** 친구방 전략은 잠근 상태에서 `isFull()`을 확인하고 카운터를 올린다.
테마방은 검사·증가를 한 문장으로 합쳐 경합 창 자체를 없앤다.

```sql
UPDATE rooms SET current_member_count = current_member_count + 1
WHERE id = :id AND current_member_count < capacity
```

영향받은 행이 0이면 정원이 찬 것이라 `RoomFullException`(HTTP 409)을 던진다. 카운터 증가와 멤버
삽입은 한 트랜잭션이라, 중복 입장으로 유니크 제약이 깨지면 롤백이 예약한 자리까지 자동으로
되돌린다.

## 3. 네 가지 전략

| 전략 | 메커니즘 | 실패 모드 | 처리량 | 쓰는 곳 |
| --- | --- | --- | --- | --- |
| 비관적 락 | `SELECT ... FOR UPDATE`로 방 행 잠그고 검사·삽입 | 같은 방 입장이 직렬화(락 대기) | 중 | 친구방 기본 |
| 낙관적 락 | `@Version` + 충돌 시 백오프 재시도(최대 50회) | 경합 심하면 재시도 폭증 | 경합 낮으면 높음 | 경합 적은 환경 |
| 분산 락 | Redisson `RLock` (`lock:room:{id}`) | 락 대기·리스 타임아웃 | 중 | 다중 인스턴스 |
| 원자적 | 조건부 단일 `UPDATE ... WHERE count < capacity` | (없음, 한 문장) | 높음 | 테마방(2000) |

네 전략은 같은 합격 테스트(`AllStrategiesConcurrencyTest`)를 통과한다. 정원 4명짜리 방에 100개
스레드가 동시에 달려들면 정확히 4명만 성공하고 96명은 거절되며, DB에도 정확히 4명만 남는다.

진짜 "동시 출발"을 만드는 게 동시성 테스트에서 제일 어렵다. 스레드를 만들면서 바로 일을 시키면
먼저 만든 스레드가 앞서 나간다. 그래서 모든 스레드를 먼저 만들어 `CountDownLatch` 앞에 세워 두고,
래치 하나를 열어 한꺼번에 출발시킨다.

## 4. 부하 테스트 — 어디까지 버티나

합격 테스트(4명)로 끝내기 아쉬워서, 정확성이 보장되는 범위를 한참 넘겨 천장을 쳐 봤다. 몇 분씩
걸려서 기본 빌드에선 태그로 빼 두고 `./gradlew stressTest`로 따로 돌린다(`StressTest`, 스레드 풀
128개). 아래 수치는 로컬 측정이라 절대값보다 경향이 핵심이다(LEDGER-008).

**실험 1 — 방 하나에 몰아넣기.** 정원 2000 테마방 하나에 시도를 5천 → 1만 → 2만으로 늘렸다.
몇 번을 던지든 들어간 사람은 정확히 2000명, 초과 0명. 처리량은 초당 500~750건 근처에서 천장을
쳤다. 모두 같은 방 행 하나를 고치려 줄을 서기 때문에, 그 행을 고치는 속도가 한계다.

**실험 2 — 방 여러 개로 흩뿌리기.** 같은 정원 방 10개에 시도 3만 개를 라운드로빈으로 나눠
던졌다. 합산 처리량이 초당 약 4,163건으로 약 6배 올랐고, 방마다 들어간 인원은 전부 정확히
2000명이었다.

결론. 정확성은 부하로 깨지지 않는다. 처리량이 필요하면 큰 방 하나에 몰지 말고 여러 방으로
분산하면 된다. 이게 방을 두 종류로 나눈 결정과 이어진다.

## 5. 초록불을 믿지 않고 가드를 부숴 본 것

테스트가 통과한다고 가드가 진짜 일하는 건 아니다. 그래서 일부러 부숴서 빨간불을 확인했다.

- 원자적 UPDATE에서 `WHERE count < capacity`만 빼니 2000짜리 방에 5000명이 그대로 들어오며
  테스트가 빨갛게 떴다. 그 한 줄이 정원을 지키고 있었다는 증거다. 확인하고 되돌렸다.
- 비관적 락에서 `@Lock`을 빼니 100스레드 중 88건이 깨지며 RED. 락이 실제로 직렬화하고 있었다.
- 도메인이 JPA에 의존하면 빌드가 깨지는 ArchUnit 규칙도 같은 식으로 부숴서 확인했다.

(전부 LEDGER-008, LEDGER-010에 기록.)
